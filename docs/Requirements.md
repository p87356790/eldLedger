# eldLedger 개발 프로젝트 요구사항 및 전체 설계

## 1. 프로젝트 개요

프로젝트명: **eldLedger**

개인 금융과 개인사업자 금융을 하나의 장부에서 관리하는 **Self-hosted 복식부기 회계 프로그램**을 개발한다.

핵심 목표는 다음과 같다.

> 사용자는 회계 지식 없이 가계부처럼 거래를 입력한다.
> 프로그램은 입력된 거래를 기반으로 내부적으로 정확한 복식부기(차변/대변) 데이터를 자동 생성한다.
> 사용자는 개인/사업을 쉽게 구분할 수 있고, 사업 관련 거래만 추출하여 세무사에게 전달할 수 있는 보고서를 생성한다.

ERPNext와 같은 기존 ERP의 복잡한 회계 용어와 UI를 그대로 사용하지 않는다.

**사용자 화면은 최대한 쉽고 직관적으로 만든다.**

# 2. 실행 환경

## 기본 실행 환경

**Windows 11 PC에서 서버 애플리케이션으로 실행한다.**

권장 구조:

```text
Windows 11 PC
    │
    └── Docker Desktop
          │
          ├── eldLedger Backend
          │      └── Python + FastAPI
          │
          ├── eldLedger Frontend
          │      └── React + TypeScript
          │
          └── Database
                 └── SQLite
```

사용자는 별도의 Windows 프로그램을 설치해서 사용하는 것이 아니라 웹브라우저로 접속한다.

예:

```text
http://localhost:8080
```

같은 네트워크의 다른 장치:

```text
http://192.168.x.x:8080
```

# 10. 개인/사업 구분

Tag만으로 개인/사업을 구분하지 않는다.

```text

```

### PERSONAL

### BUSINESS

### MIXED

개인과 사업이 하나의 결제에 섞인 거래

# 15. Transaction과 Journal을 분리

매우 중요하다.

사용자가 입력한 거래와 실제 회계분개를 동일한 테이블로 관리하지 않는다.

예:

```text
Transaction

"국민카드로 사무용품 50,000원"
```

과

```text
Journal Entry

차변 사무용품비       50,000
대변 카드미지급금     50,000
```

을 별도의 구조로 관리한다.

---

# 16. 복식부기 무결성

모든 Journal Entry는 반드시:

```text
SUM(debit) == SUM(credit)
```

이어야 한다.

저장 전에 검증한다.

불균형 분개는 저장할 수 없도록 한다.

---

# 17. 확정된 거래 수정

확정된 회계분개를 단순 UPDATE/DELETE하지 않는다.

기본 구조:

```text
작성
 ↓
확정
 ↓
수정 필요
 ↓
취소/역분개
 ↓
새로운 거래
```

회계 기록의 추적성을 유지한다.

# 39. 개발 시 반드시 지켜야 할 것

1. **복식부기 데이터 구조를 먼저 정확하게 설계한다.**
2. UI를 먼저 만들고 나중에 회계 기능을 붙이지 않는다.
3. Transaction과 Journal Entry를 분리한다.
4. 모든 Journal Entry의 차변 합계와 대변 합계는 반드시 일치해야 한다.
5. 이미 확정된 회계 데이터를 임의로 삭제하지 않는다.
6. 모든 금액 계산에서 Decimal 또는 정수 기반 금액을 사용한다.
7. 테스트 코드를 작성한다.
8. 자동분개 규칙은 단위 테스트를 작성한다.
9. 보고서는 DB의 Journal 데이터를 기반으로 생성한다.
10. 보고서 계산을 화면에서 임의로 하지 않는다.
11. 모든 중요 기능은 API와 DB 구조를 문서화한다.
12. 한국어 UI를 기본 언어로 한다.
13. 회계 전문용어는 일반 사용자에게 최대한 숨긴다.
14. Windows + Docker 환경에서 처음부터 실제 실행 가능한 상태를 유지한다.

# 40. 첫 번째 개발 목표

처음부터 모든 기능을 한번에 구현하지 않는다.

먼저 다음 시나리오를 완전히 동작시키는 것을 목표로 한다.

### 테스트 시나리오

사용자가 다음 거래를 입력한다.

```text
2026-09-01
사업
국민카드
사무용품
50,000원
영수증 첨부
```

사용자가 저장하면:

```text
Transaction 생성
       ↓
자동 Journal Entry 생성
       ↓
차변 사무용품비 50,000
대변 카드미지급금 50,000
       ↓
거래원장에서 확인
       ↓
계정별 원장에서 확인
       ↓
시산표에 반영
       ↓
사업 보고서에 반영
       ↓
Excel로 출력
```

이 전체 흐름이 정상적으로 동작하는 것을 **첫 번째 마일스톤**으로 한다.
